## Recommendation

Finish the executable legacy-parity contract in [#39](https://github.com/williamzujkowski/progress-quest-ii/issues/39) next, beginning with a modern-versus-legacy encounter-output comparison, followed by the missing progression and market boundary vectors. Then unblock the pure `advanceGame` seam in [#42](https://github.com/williamzujkowski/progress-quest-ii/issues/42). This is the smallest next slice that makes the later checkpoint and PWA work trustworthy: ProgQuest's accepted roadmap defines RNG continuation, task ordering, progression, loot, currency, and activity text as observable behavior, and explicitly orders trace coverage before the transition seam and save/RNG compatibility ([roadmap](../modernization-roadmap.md#phase-0--make-correctness-observable)).

## Evidence

- As written, the four oracle fixtures then present proved that the **legacy harness** reproduced stored expected output, and the test never ran the modern transition against those vectors (`scripts/test-legacy-oracle.mjs`, retired in #381). Both halves have since changed: there are fifteen recordings and every one is now compared against the modern transition by `src/__tests__/goldens/transitionParity.test.ts`. The modern game loop still combines mechanics, Zustand mutation, sound side effects, strings, and RNG consumption in one method ([game store](../../src/state/gameStore.ts#L61-L125)). A deterministic modern implementation can therefore remain deterministically wrong.
- The legacy baseline persists a resumable RNG snapshot and attempts to save the active game on unload, while explicitly accepting possible data loss (legacy `main.js` (`main.js:985-1001`)). The modern PRNG already exposes the required four-number continuation seam ([`prng.ts`](../../src/engine/prng.ts#L84-L98)), but the modern app constructs the default character on every store initialization and has no startup hydration path ([`gameStore.ts`](../../src/state/gameStore.ts#L25-L33), [`App.tsx`](../../src/App.tsx#L38-L41)).
- The runtime error boundary, bounded diagnostics, build correlation, and browser/React capture are merged, so a second diagnostics framework is not the next gap ([`main.tsx`](../../src/main.tsx), [`diagnostics.ts`](../../src/state/diagnostics.ts)). [#45](https://github.com/williamzujkowski/progress-quest-ii/issues/45) remains open for expected capability failures and future PWA lifecycle diagnostics; tracker state should not be mistaken for an absent foundation.
- Save hardening is partly implemented: encoded input is bounded before decode, roster reads revalidate every entry, and prototype-key collisions use a null-prototype object ([`saveManager.ts`](../../src/state/saveManager.ts#L31-L62), [`saveManager.ts`](../../src/state/saveManager.ts#L76-L103)). [#20](https://github.com/williamzujkowski/progress-quest-ii/issues/20) is still materially incomplete because the schema does not enforce `currentProgress <= maxProgress` or `elapsedMs <= durationMs`, and it has no explicit version/migration envelope ([`schemas.ts`](../../src/state/schemas.ts#L53-L82)). Finish those boundary rules before reusing the schema for checkpoints.
- A checkpoint should write a single validated, versioned value, debounce routine writes, and flush when the document becomes hidden. MDN identifies the transition to `hidden` as the last reliably observable page event; `pagehide` is a compatible fallback but is not reliable on mobile ([MDN `visibilitychange`](https://developer.mozilla.org/en-US/docs/Web/API/Document/visibilitychange_event#usage_notes), [MDN `pagehide`](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event#usage_notes)). The HTML Standard also warns that `localStorage` has no cross-agent locking and that writes can fail from quota or user policy, so startup must distinguish missing, corrupt, and unavailable storage and must not overwrite after a failed read ([WHATWG Web Storage](https://html.spec.whatwg.org/multipage/webstorage.html#the-storage-interface)).
- Offline behavior is genuinely absent: the README states that there is no manifest, service worker, update handling, or offline E2E coverage ([README](../../README.md#pwa-status-without-the-marketing-fog)). A service worker is the platform interception/cache mechanism for offline requests, and Playwright can place a browser context offline for an acceptance test ([MDN service workers](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers), [Playwright offline emulation](https://playwright.dev/docs/emulation#offline)). Shipping it before deterministic checkpoint restore would make the shell survive a reload while the active hero does not.
- Supply-chain work in [#46](https://github.com/williamzujkowski/progress-quest-ii/issues/46) remains valuable: CI uses mutable major Action tags ([workflow](../../.github/workflows/ci.yml#L15-L29)), while GitHub says a full commit SHA is the only immutable Action reference ([GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions)). It ranks after correctness/session continuity because the current pipeline already gates lint, types, unit/contracts, build, audit, and Chromium E2E with read-only CI permissions.

## Ranked candidates

1. **Finish #39's modern-versus-legacy transition contract, then unblock #42.** Highest correctness and maintainability leverage; current tests validate the oracle but do not compare the shipped engine, and the pure seam is intentionally blocked on this evidence. Land encounter output first, then add progression, market sell/buy, and finite/progress invariant vectors before closing #39.
2. **Implement #43's validated active-session checkpoint.** Highest immediate player-reliability gain; reload currently recreates `Krg`. Persist character, exact RNG state, task remainder, pause state, and a bounded activity tail; hydrate once, debounce, flush on `visibilitychange`, and preserve the last-known-good record on any read/validation failure. Gate this on completing #20's cross-field/version rules and the required serialization/security vote.
3. **Implement #4's update-safe offline PWA plus lifecycle diagnostics.** Adds the promised manifest, Pages-subpath service-worker scope, versioned app-shell cache, explicit update action, rollback/unregister path, and online-first/offline-reload/update E2E. Build it after checkpoint restore so “works offline” includes deterministic session continuity, and extend the existing diagnostic vocabulary rather than adding a logging subsystem.

After these, take [#46](https://github.com/williamzujkowski/progress-quest-ii/issues/46) and [#47](https://github.com/williamzujkowski/progress-quest-ii/issues/47) as the delivery-maintainability tranche. Do not add remote telemetry, a service-worker framework, an event bus, or a worker-based engine until measured complexity requires one.
